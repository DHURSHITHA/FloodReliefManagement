⚠️ One known, pre-existing failure — here’s exactly how to fix it

Test: shared/src/schemas/camp.schema.test.js — "createCampSchema defaults every facility flag to false and toilets_count to 0 when omitted"

What it expects: when a camp is created without specifying facility flags (electricity, water_supply, medical_tent, etc.) or a toilets_count, the validation schema should silently fill in false for every omitted flag and 0 for the count — so a partially-filled form still produces a complete, well-typed record.

Why it’s failing: the schema’s default values have drifted from what this test expects — this has been a known, documented gap since the Milestone 1 verification pass and reproduces identically on every commit since, including before Milestone 2 began. It is not a regression introduced by SOS or Donations work.

How to confirm and fix it: open shared/src/schemas/camp.schema.js, find createCampSchema, and check the .default() calls (or superRefine/transform step) on the facility-flag fields and toilets_count. Run npm run test --workspace shared -- src/schemas/camp.schema.test.js to see the exact expected-vs-received values Vitest prints, adjust the schema to match, then re-run the same command to confirm it goes green.

Spotlight — key edge cases

17 hand-picked tests that each guard against a specific, realistic way the system could fail silently — explained in full for anyone who wants to understand exactly what they prove.

Edge case Server

“never issues two lots under concurrent first-time receipt”

server/src/modules/resources/resources.service.test.js

What could go wrong without it — Five simultaneous "first donation to this camp/item" confirmations were fired at once. A naive implementation checks "does a lot exist?", finds none, and inserts — and under real concurrency, more than one request can pass that check before either insert lands, creating duplicate stock lots that silently double-count inventory.

What the test proves — A MongoDB partial unique index on {camp_id, item_id, source: "donation"} makes the database itself the referee: only one insert can win, and every loser retries into an update on the winner’s document instead. This was a real bug caught mid-build (Milestone 2 Plan 2) — the first version of this function failed this exact test.

Edge case Server

“never overshoots under concurrent reservations for the last bed”

server/src/modules/camps/camps.service.test.js

What could go wrong without it — Two families are checked in for the very last open bed at the same moment. Without a safeguard, both requests could read "1 bed left", both proceed, and the camp ends up recording more beneficiaries than its physical capacity.

What the test proves — The slot reservation runs as an atomic, transaction-wrapped update rather than a read-then-write — the database guarantees only one of the two requests can actually claim the last bed; the other is told, correctly, that the camp is full.

Edge case Server

“never grants more than capacity under two concurrent requests for the last slot”

server/src/modules/camps/camps.service.test.js

What could go wrong without it — The same race as above, applied to volunteer sign-ups instead of beneficiary beds.

What the test proves — Partial grants are supported (fewer slots than requested is a valid outcome) but the sum across every concurrent grant can never exceed the camp’s declared volunteer capacity.

Edge case Server

“never issues the same code twice under concurrent calls”

server/src/core/idGenerator.test.js

What could go wrong without it — Every human-facing code in the system — BEN-1001, SOS-1042, DON-1007 — comes from this one counter function. If two requests could ever receive the same number, two different records would carry an identical, supposedly-unique reference code, breaking every lookup and every printed receipt that cites it.

What the test proves — Tested three times independently (beneficiary, SOS and donation counters) with a burst of concurrent calls against each, using MongoDB’s atomic $inc-with-upsert rather than a read-modify-write.

Edge case Server

“refuses to decide an already-decided donation twice”

server/src/modules/donations/donations.test.js

What could go wrong without it — An admin double-clicks "Confirm", or two admin tabs are open on the same pending donation. Deciding it twice could post the same stock donation into inventory a second time, or overwrite a rejection reason with a second, contradictory decision.

What the test proves — A donation can only be decided while its status is "pending" — the second attempt is refused outright with a 409 Conflict rather than silently repeating the effect.

Edge case Server

“a donor cannot read another donor’s profile through any donation payload”

server/src/modules/donations/donations.test.js

What could go wrong without it — A malicious or merely curious donor account tries to see who else has donated, and how much, by reading their own donation list.

What the test proves — Part of a four-test "cross-role leakage" group written specifically to fail if any listing endpoint returns data scoped too broadly — the M1 project shipped a real camp-scope bug once because its tests only ever used an admin account; every M2 module now includes a test written from the adversary’s point of view, not just the happy path.

Edge case Server

“an admin-recorded donation for donor A cannot be listed under donor B’s account”

server/src/modules/donations/donations.test.js

What could go wrong without it — An admin phones in a donation on behalf of a real donor (a cheque received by post). If the donor linkage were even slightly wrong, that donation could appear in a completely unrelated donor’s history.

What the test proves — The admin-recorded donation is verified to appear only under the donor it was actually recorded for.

Edge case Server

“rejects a material donation confirmation with no target camp”

server/src/modules/donations/donations.test.js

What could go wrong without it — A donor records "100kg of rice" without saying which camp it is for. If confirmation were allowed anyway, the stock increase would have nowhere valid to land.

What the test proves — Confirmation of a material donation is refused with a clear 400 until a target camp is set — stock has to land somewhere before it can be posted.

Edge case Server

“adds donated stock to an existing donation-sourced lot rather than creating a second one”

server/src/modules/donations/donations.test.js

What could go wrong without it — Two separate donations of the same item to the same camp, confirmed one after another, could otherwise create two separate inventory lots for what should be one running total.

What the test proves — The second confirmation is verified to increase the existing lot’s quantity rather than fragmenting stock across multiple records — the read side of the same concurrency-safe design spotlighted above.

Edge case Server

“rejects a tampered token”

server/src/middleware/auth.middleware.test.js

What could go wrong without it — Someone edits the payload of their own JWT (say, changing their role from "donor" to "admin") and re-sends it, hoping the server trusts the client-supplied content.

What the test proves — The signature check fails on any modification to the token, however small, and the request is rejected before it reaches any route handler.

Edge case Server

“rejects a token whose user has since been disabled”

server/src/middleware/auth.middleware.test.js

What could go wrong without it — An admin disables a misbehaving account, but that account’s existing 15-minute access token would otherwise keep working until it naturally expires.

What the test proves — Every authenticated request re-checks the account’s live status in the database, so disabling an account takes effect immediately, not after up to 15 minutes.

Edge case Server

“refuses an official acting on someone else’s camp”

server/src/middleware/auth.middleware.test.js

What could go wrong without it — A camp official at Camp A tries to act on a record that belongs to Camp B — either by guessing an id or through a compromised session.

What the test proves — The reusable requireOwnCamp guard refuses the action for every role except admin, regardless of what the request body claims.

Edge case Server

“rejects resolving without a note, requires one to close, appends the timeline, and notifies the reporter”

server/src/modules/sos/sos.test.js

What could go wrong without it — An emergency gets marked "resolved" with no record of what was actually done — indistinguishable, months later, from an emergency nobody ever responded to.

What the test proves — A closing status with no explanation is refused outright, the same discipline the complaints module enforces for its own closing statuses.

Edge case Server

“copies the routed contact rather than referencing it live”

server/src/modules/sos/sos.test.js

What could go wrong without it — A camp’s hospital contact number is edited three months after an emergency was raised against it — if the SOS record only stored a reference, the historical record of who was actually called would silently change.

What the test proves — The hospital or police contact is copied onto the SOS record at the moment it is created, so the record reflects who was contacted at the time, permanently.

Edge case Server

“refuses an official reviewing another camp’s complaint”

server/src/modules/complaints/complaints.test.js

What could go wrong without it — The same cross-camp boundary as SOS and fund requests, applied to complaints — an official should never be able to close out a complaint raised at a camp they do not run.

What the test proves — Camp scoping is checked before any review action is applied, not just before the list is shown.

Edge case Server

“(Aadhaar-based deduplication)”

server/src/modules/intake/intake.service.test.js

What could go wrong without it — The same family is registered twice — once during an initial rush, once later by a different volunteer — which would double-count them in every capacity and ration calculation.

What the test proves — Registration is keyed against a one-way HMAC of the Aadhaar number, so a duplicate is caught even though the plaintext number is never stored in a searchable form.

Edge case Shared

“detects any single-digit typo”

shared/src/aadhaar.test.js

What could go wrong without it — A volunteer mistypes one digit of a 12-digit Aadhaar number while registering a family under pressure.

What the test proves — The Verhoeff checksum algorithm (the same one India’s UIDAI uses) mathematically guarantees any single-digit error changes the checksum, so the form rejects it immediately rather than silently registering the wrong person.
